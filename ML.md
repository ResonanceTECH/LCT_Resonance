


# ТЗ для ML-разработчика

## 1. Задача ML-модуля

ML-модуль отвечает за интеллектуальную обработку профилей кандидатов и требований работодателей.

В рамках MVP он должен решать три основные задачи:

1. **Категоризация кандидата** по профессиональному направлению.
2. **Расчет соответствия кандидата вакансии / потребности работодателя.**
3. **Ранжирование кандидатов** и формирование понятного объяснения, почему конкретный кандидат подходит.

Дополнительно ML может использовать:

- данные профиля кандидата;
- заявленные навыки;
- заявленный грейд;
- результаты тестирования;
- подтвержденные достижения ФСП;
- требования вакансии;
- карьерные предпочтения кандидата.

Важно: достижения ФСП являются **дополнительным подтвержденным сигналом**, но не должны автоматически доказывать знание конкретной технологии. Например, участие в соревновании ФСП не означает автоматически, что кандидат знает React или Python.

---

# 2. Функциональные требования

### ML-01. Нормализация навыков

Система должна приводить разные варианты написания одного навыка к единому виду.

Например:

```javascript
```

```javascript
React.js → React
ReactJS → React
JS → JavaScript
TS → TypeScript
Postgres → PostgreSQL
Py → Python
```

На вход:

```javascript
```

```javascript
["React.js", "TS", "Postgres"]
```

На выход:

```javascript
```

```javascript
["React", "TypeScript", "PostgreSQL"]
```

Это необходимо, чтобы matching не считал 

```javascript
React.js
```

 и 

```javascript
React
```

 разными навыками.

---

### ML-02. Категоризация кандидата

ML должен определять профессиональное направление кандидата.

Минимальный набор категорий для MVP можно зафиксировать заранее:

```javascript
```

```javascript
Frontend
Backend
Mobile
ML / Data Science
Data Engineering
DevOps
QA
Cybersecurity
Algorithms
Other
```

При категоризации можно учитывать:

- специализацию, которую выбрал кандидат;
- навыки;
- опыт;
- данные ФСП;
- дисциплины соревнований;
- роль кандидата в соревнованиях.

При этом выбранная самим кандидатом специализация должна иметь больший вес, чем косвенные признаки.

Пример:

```javascript
```

```javascript
{
  "candidate_id": 15,
  "category": "Frontend",
  "confidence": 0.91,
  "reasons": [
    "Кандидат указал специализацию Frontend",
    "В профиле указаны React и TypeScript"
  ]
}
```

---

### ML-03. Работа с грейдом

Кандидат самостоятельно указывает свой предполагаемый уровень:

```javascript
```

```javascript
Intern
Junior
Middle
Senior
```

Результаты тестирования должны использоваться как дополнительный сигнал при оценке профиля.

При этом система **не должна автоматически понижать заявленный грейд кандидата**, если результат теста оказался ниже ожидаемого.

Например:

```javascript
```

```javascript
{
  "declared_grade": "Middle",
  "test_score": 62,
  "grade_status": "not_confirmed"
}
```

Но система не должна самостоятельно заменять:

```javascript
```

```javascript
Middle → Junior
```

Результат тестирования может влиять на положение кандидата внутри категории и на matching, если это предусмотрено согласованной формулой.

---

### ML-04. Обработка данных ФСП

ML должен уметь использовать структурированные данные ФСП как дополнительный сигнал при ранжировании.

Возможные входные данные:

```javascript
```

```javascript
{
  "discipline": "Программирование продуктовое",
  "competition": "Название соревнования",
  "place": 2,
  "role": "Участник",
  "rank": "1 разряд",
  "verified": true
}
```

ML не должен изменять статус 

```javascript
verified
```

.

Backend получает данные через FSP Adapter / Mock API и передает ML уже подготовленные данные.

ML может преобразовывать достижения в признаки для ranking/matching.

Например:

```javascript
```

```javascript
есть подтвержденные достижения;
количество достижений;
релевантная дисциплина;
наличие разряда;
результаты соревнований.
```

# 3. Matching кандидата и вакансии

### ML-05. Расчет Match Score

Для пары:

```javascript
```

```javascript
Candidate + Vacancy
```

модуль должен возвращать показатель соответствия:

```javascript
```

```javascript
0–100%
```

Для MVP необязательно обучать полноценную ML-модель. Допустим и предпочтителен объяснимый baseline scoring.

Например:

| Критерий | Вес |
|----|----|
| Совпадение навыков | 40% |
| Специализация | 25% |
| Результаты тестирования / подтверждение уровня | 15% |
| Релевантные достижения ФСП | 10% |
| Формат и карьерные предпочтения | 10% |

Точные веса ML-разработчик может предложить после анализа данных.

**Зарплату лучше использовать как отдельное условие совместимости**, а не пытаться «предсказывать» зарплату кандидата.

Например, если кандидат ожидает от 200 000 ₽, а вакансия предлагает максимум 120 000 ₽, это должно явно отображаться как несовпадение условий.

---

### ML-06. Matching навыков

Для вакансии:

```javascript
```

```javascript
{
  "required_skills": [
    "React",
    "TypeScript",
    "Redux",
    "Git"
  ]
}
```

и кандидата:

```javascript
```

```javascript
{
  "skills": [
    "React",
    "TypeScript",
    "Git",
    "Python"
  ]
}
```

модуль должен вернуть:

```javascript
```

```javascript
{
  "matched_skills": [
    "React",
    "TypeScript",
    "Git"
  ],
  "not_listed_skills": [
    "Redux"
  ]
}
```

Важно использовать формулировку **«не указан в профиле»**, а не «кандидат не знает Redux».

Отсутствие навыка в профиле не доказывает отсутствие этого навыка у человека.

---

# 4. Объяснимость результата

### ML-07. Match Explanation

Для каждого рассчитанного Match Score модуль должен возвращать причины результата.

Например:

```javascript
```

```javascript
{
  "candidate_id": 15,
  "vacancy_id": 7,
  "match_score": 87,

  "matched_skills": [
    "React",
    "TypeScript",
    "Git"
  ],

  "not_listed_skills": [
    "Redux"
  ],

  "reasons": [
    "Совпадает специализация Frontend",
    "Совпадают 3 из 4 обязательных навыков",
    "Подходит удаленный формат работы",
    "Есть подтвержденные достижения ФСП"
  ]
}
```

Это критичная часть MVP.

Работодатель должен видеть не просто:

> 87% Match

а:

> 87% Match, потому что совпали специализация, 3 из 4 навыков, формат работы и есть релевантные подтвержденные достижения.

---

# 5. Ранжирование кандидатов

### ML-08. Ranking

После расчета Match Score ML должен иметь возможность отсортировать кандидатов для конкретной вакансии.

Например:

```javascript
```

```javascript
[
  {
    "candidate_id": 12,
    "match_score": 92
  },
  {
    "candidate_id": 17,
    "match_score": 86
  },
  {
    "candidate_id": 31,
    "match_score": 79
  }
]
```

Работодатель в первую очередь должен получать наиболее релевантных кандидатов.

---

### ML-09. Ранжирование внутри категории

По исходному ТЗ требуется учитывать положение кандидата внутри своей категории.

Категория может быть представлена как сочетание:

```javascript
```

```javascript
специализация + грейд
```

Например:

```javascript
```

```javascript
Frontend / Junior
Backend / Junior
Frontend / Middle
ML / Junior
```

Внутри категории кандидаты могут ранжироваться на основании:

- результатов тестирования;
- заполненности релевантной части профиля;
- подтвержденных достижений ФСП;
- релевантности навыков.

Пример результата:

```javascript
```

```javascript
{
  "category": "Frontend / Junior",
  "candidate_id": 15,
  "category_score": 84
}
```

При этом для MVP не обязательно показывать пользователю жесткое «место №17 среди Junior Frontend». Достаточно использовать этот score для сортировки.

---

# 6. Кандидаты без данных ФСП

### ML-10. Fallback-сценарий

Matching должен работать даже в том случае, если у кандидата нет достижений ФСП.

То есть:

```javascript
```

```javascript
{
  "fsp_achievements": []
}
```

не является ошибкой.

В этом случае score рассчитывается на основании остальных доступных данных:

- специализации;
- навыков;
- опыта;
- грейда;
- тестирования;
- карьерных предпочтений.

Отсутствие истории ФСП не должно автоматически исключать кандидата из выдачи.

# 7. Контракт ML → Backend

Frontend **не должен напрямую обращаться к ML**.

Схема:

```javascript
```

```javascript
Frontend
   ↓
Backend
   ↓
ML / Matching
   ↓
Backend
   ↓
Frontend
```

Backend является единой точкой API для клиента.

### Пример входа в matching

```javascript
```

```javascript
{
  "candidate": {
    "id": 15,
    "specialization": "Frontend",
    "declared_grade": "Junior",
    "skills": [
      "React",
      "TypeScript",
      "Git"
    ],
    "experience_months": 10,
    "salary_from": 150000,
    "work_formats": [
      "remote"
    ],
    "test": {
      "score": 82
    },
    "fsp_achievements": [
      {
        "discipline": "Программирование продуктовое",
        "place": 2,
        "verified": true
      }
    ]
  },

  "vacancy": {
    "id": 7,
    "specialization": "Frontend",
    "grade": "Junior",
    "required_skills": [
      "React",
      "TypeScript",
      "Redux",
      "Git"
    ],
    "salary_from": 170000,
    "salary_to": 220000,
    "work_format": "remote"
  }
}
```

### Пример ответа

```javascript
```

```javascript
{
  "candidate_id": 15,
  "vacancy_id": 7,

  "match_score": 89,

  "components": {
    "skills": 36,
    "specialization": 25,
    "test": 13,
    "fsp": 7,
    "preferences": 8
  },

  "matched_skills": [
    "React",
    "TypeScript",
    "Git"
  ],

  "not_listed_skills": [
    "Redux"
  ],

  "salary_compatible": true,
  "work_format_compatible": true,

  "reasons": [
    "Совпадает специализация",
    "Совпадают 3 из 4 обязательных навыков",
    "Высокий результат тестирования",
    "Есть подтвержденные достижения ФСП",
    "Совпадает формат работы"
  ]
}
```

Такой формат очень удобен и Backend, и Frontend: фронту уже не приходится самостоятельно разбираться, почему получился 

```javascript
89%
```

.

# 8. Что относится к ML, а что нет

Я бы сразу зафиксировала границы, потому что здесь команда легко может начать делать одно и то же.

| Задача | Ответственный |
|----|----|
| Хранение профиля | Backend |
| Хранение вакансии | Backend |
| Получение данных ФСП | Backend |
| Проверка ```javascript
verified
``` | Backend / FSP Adapter |
| Хранение результатов тестов | Backend |
| Проведение тестирования | Backend + Frontend |
| Нормализация навыков | ML |
| Категоризация кандидата | ML |
| Расчет Match Score | ML |
| Ranking | ML |
| Формирование причин matching | ML |
| Отправка приглашения | Backend |
| Статусы приглашений | Backend |
| Отображение Match Score | Frontend |
| Фильтры интерфейса | Frontend + Backend |

То есть ML **не занимается пользователями, авторизацией, приглашениями, контактами, CRUD вакансий и ФСП API**.

---

# 9. Что делать с тестированием

Здесь я бы не нагружала ML-разработчика генерацией вопросов через LLM.

Из ТЗ следует необходимость тестирования заявленного грейда, но это не означает, что именно ML должен генерировать и проверять тесты.

Для MVP проще:

```javascript
```

```javascript
Candidate
↓
выбирает Junior
↓
проходит заранее подготовленный Junior-тест
↓
Backend считает/хранит результат
↓
ML получает score
↓
score учитывается в ranking
```

Например:

```javascript
```

```javascript
Junior Frontend
Test score: 82/100
```

ML использует 

```javascript
82
```

 как один из признаков.

**Автоматическая генерация тестовых заданий через LLM** уже может быть продуктовой гипотезой, но я бы не ставила ее в P0.

# 10. Приоритеты ML на хакатон

### P0 - обязательно

 1. Зафиксировать входные данные кандидата и вакансии.
 2. Нормализовать навыки.
 3. Категоризировать кандидатов.
 4. Реализовать baseline Match Score.
 5. Учитывать результаты тестирования.
 6. Учитывать подтвержденные достижения ФСП.
 7. Ранжировать кандидатов под вакансию.
 8. Возвращать объяснение matching.
 9. Корректно работать без FSP achievements.
10. Отдать Backend стабильный формат input/output.

### P1 - если P0 готов

- синонимы и расширенный словарь навыков;
- более умное определение релевантности достижений ФСП;
- nice-to-have и must-have навыки;
- улучшение весов scoring;
- семантическое сравнение вакансии и профиля.

### P2 - только если остается время

Это уже скорее **продуктовые гипотезы**, а не обязательные требования исходного ТЗ:

- embeddings;
- LLM-анализ текста вакансии;
- автоматическое извлечение стека из описания вакансии;
- AI-рекомендации кандидату;
- сложная персонализация ranking.

Для 4-дневного хакатона я бы **не обучала отдельную ML-модель только ради того, чтобы в проекте был ML**. Если нет нормального датасета, объяснимый scoring будет надежнее и его проще защитить перед жюри.

# 11. Definition of Done для ML

ML-часть MVP можно считать готовой, если на демо Backend может передать ей кандидата и вакансию, а в ответ получить что-то вроде:

```javascript
```

```javascript
{
  "match_score": 91,
  "category": "Frontend / Junior",
  "matched_skills": [
    "React",
    "TypeScript",
    "Git"
  ],
  "not_listed_skills": [
    "Redux"
  ],
  "salary_compatible": true,
  "reasons": [
    "Совпадает специализация",
    "Совпадают основные навыки",
    "Подходит формат работы",
    "Хороший результат тестирования",
    "Есть подтвержденные достижения ФСП"
  ]
}
```

И на основании этого Backend может вернуть работодателю **отсортированный список кандидатов с Match Score и причинами соответствия**.

## Что я бы конкретно поставила ML-разработчику на первые 4 дня

**День 1:** согласовать с Backend JSON-контракт, категории кандидатов, признаки, словарь навыков и первую формулу scoring.

**День 2:** реализовать нормализацию навыков, категоризацию и baseline matching.

**День 3:** добавить FSP-признаки, результаты тестирования, ranking и explainability. Прогнать на 10-20 заранее подготовленных кандидатах и 3-5 вакансиях.

**День 4:** интеграция с Backend, исправление крайних случаев, фиксация весов и подготовка стабильных demo results.

Самое важное для вашей команды сейчас: **Backend и ML уже на первом созвоне должны договориться о JSON-контракте**. Иначе ML сделает один формат данных, Backend другой, а на третий день придется переделывать интеграцию.

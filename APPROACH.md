# Выбранный подход: подбор и тестирование

Как в MVP Resonance ранжируем кандидатов под вакансию и как подтверждаем грейд тестом. Подробности реализации лежат в `ML.md`, `Backend.md` и сервисе `ml/`.

## 1. Общий принцип

На хакатоне мы не обучаем непрозрачную модель. Датасета «правильных» пар кандидат-вакансия нет, а жюри всё равно спросит, почему человек оказался выше в выдаче. Поэтому схема такая:

1. Тест подтверждает категорию (специализация + грейд). В Talent Pool по вакансии попадают только те, у кого эта категория уже подтверждена.
2. Уже внутри пула считаем понятный Match Score и отдаём причины. Работодатель видит не только процент, но и из чего он сложился.
3. Достижения ФСП учитываем как дополнительный подтверждённый сигнал. Участие в соревновании само по себе не доказывает знание React или Python.
4. Зарплату и формат работы не «предсказываем». Это явные флаги совместимости: подходит или нет.

Поток данных:

```text
Кандидат: профиль → тест → подтверждённая категория → (по желанию ФСП)
                              ↓
Работодатель: вакансия → Talent Pool (жёсткий фильтр по категории)
                              ↓
                 матчер: Match Score + причины + порядок в выдаче
```

На Frontend остаётся только отображение. Score и оценка теста считаются на Backend и в ML-сервисе.

## 2. Механика подбора



### 2.1. Две ступени


| Ступень            | Что происходит                                                                                  | Зачем так                                           |
| ------------------ | ----------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| Жёсткий фильтр     | В выдаче по вакансии остаются кандидаты с подтверждённой специализацией и грейдом этой вакансии | Пул сразу «по делу»; тест перестаёт быть декорацией |
| Мягкий score 0-100 | Сортировка внутри уже отфильтрованного пула                                                     | Отличаем более сильных при одной и той же категории |


Специализацию в формуле `/rank` повторно не начисляем: Backend её уже отфильтровал. Иначе один факт давал бы очки дважды.

### 2.2. Формула Match Score для Talent Pool

```text
score = 0.50·test + 0.25·skills + 0.15·fsp + 0.10·conditions
```

Каждый компонент сначала считается в шкале 0..100, потом умножается на вес.


| Компонент  | Вес | Смысл                                                                                                                       |
| ---------- | --- | --------------------------------------------------------------------------------------------------------------------------- |
| test       | 50% | Балл теста в той же категории. Если категория не совпала, вклад теста равен нулю                                            |
| skills     | 25% | Взвешенное пересечение стека после нормализации написания. Обязательный навык весит 2, желательный 1                        |
| fsp        | 15% | Только `verified` достижения: тип результата, разряд, близость дисциплины к вакансии. Пустой ФСП даёт 0 и не ломает матчинг |
| conditions | 10% | Совпадение формата работы и потолка зарплаты вакансии с ожиданиями кандидата (поровну)                                      |


В `ML.md` есть вариант весов 40/25/15/10/10 со специализацией внутри формулы. Его оставляем для мягкого или межкатегорийного анализа. Основной score Talent Pool так не считаем.

### 2.3. Навыки и формулировки

Нормализуем написание: `React.js` и `ReactJS` становятся `React`, `TS` становится `TypeScript`, `Postgres` становится `PostgreSQL`.

В ответе матчера есть `matchedSkills` и `missingInProfileSkills`. Missing значит «не указан в профиле», а не «кандидат этого не умеет». Пустая строка в анкете не доказывает отсутствие навыка.

### 2.4. Объяснения и порядок в выдаче

К каждому match приходят структурированные причины с кодами вроде `SKILLS_REQUIRED`, `TEST_SCORE`, `FSP_VERIFIED`, `SALARY_MISMATCH`. Текст подписей собирает Backend (и дальше Frontend), чтобы baseline и внешний ML говорили одними словами.

Сортировка: выше score, при равенстве выше вклад теста, затем внутренний `categoryScore`, затем стабильный `candidateId`.

`categoryScore` (тест, заполненность профиля, ФСП, ширина стека) нужен только чтобы упорядочить людей внутри категории. Публичное «место №17 среди Junior Frontend» в MVP не показываем.

### 2.5. Почему так

Размеченного датасета пар нет. На хакатоне обученная модель легко переобучается и плохо объясняется. Взвешенный score с причинами прямо закрывает требование ТЗ «почему этот кандидат».

Жёсткий фильтр и мягкий score разделены: одно решает, кого вообще показывать, другое решает, кого показать выше. Тест из-за этого не превращается в ещё один процент в каше признаков.

Вес теста 50% выше черновых 15% из `ML.md` намеренно. После фильтра по категории именно результат теста лучше всего отличает кандидатов друг от друга; навыки и ФСП уточняют картину.

ФСП не обязателен. Нет достижений - нет штрафа исключением из выдачи, только нулевой вклад этого компонента.

Зарплата остаётся явным несовпадением условий, а не спрятанным фактором внутри регрессии.

## 3. Механика тестирования кандидатов



### 3.1. Роль теста

Тест подтверждает заявленный грейд в выбранной специализации. Сам по себе он Match Score не заменяет, а даёт входной сигнал для него.

```text
Кандидат выбирает специализацию и грейд
        ↓
Сессия из 10 вопросов (темы и сложность по blueprint)
        ↓
Backend считает score (пропуск считается ошибкой)
        ↓
score ≥ 70 → категория подтверждена, сохраняется last_test_score
score < 70 → грейд не подтверждён; заявленный грейд система не понижает
```

Инварианты:

- Заявленный грейд и результат теста в продукте живут раздельно.
- Провал никогда не откатывает уже подтверждённую категорию вниз.
- Смена подтверждённой категории ограничена кулдауном (`GRADE_COOLDOWN_DAYS`).
- Правильные ответы на Frontend до завершения сессии не отдаются.

Проведение теста и хранение результатов - зона Backend и Frontend. ML получает готовый `testScore` и статус грейда. Генерацию вопросов через LLM в P0 не делаем.

### 3.2. Как собирается тест

Один статичный банк с готовыми ответами на хакатоне быстро утекает между участниками. Основная единица - шаблон (generator):

```text
специализация + грейд
        ↓
blueprint (темы × число слотов), например Frontend: JS×3, React×3, HTTP×2, Architecture×2
        ↓
на слот: по возможности generator(seed) → уникальный экземпляр
        ↓
добор из static-пула (архитектура, практики)
        ↓
варианты ответа перемешиваются; правильный вариант остаётся на сервере
```

Сгенерированные задания параметризованы: SQL join, вывод кода, Big-O, event loop и похожие вещи. У разных кандидатов разные входные данные и разные правильные ответы при сопоставимой сложности.

Статические вопросы оставляем там, где шаблон плохо ложится. Их долю ограничиваем, чтобы тест не сводился к заучиванию пула.

Экземпляры фиксируются в `test_session_items` при старте, чтобы сессию можно было воспроизвести по seed. Стек и `requiredSkills` могут смещать выбор шаблонов внутри темы, но не ломают число вопросов и сопоставимость баллов.

### 3.3. Связь теста с подбором


| Событие                     | Эффект                                                              |
| --------------------------- | ------------------------------------------------------------------- |
| Тест не сдан или не пройден | Кандидата нет в Talent Pool по категории этой вакансии              |
| Тест сдан (≥70)             | Жёсткий фильтр пропускает; `testScore` даёт до половины Match Score |
| Высокий балл                | Плюс в объяснении (`TEST_SCORE`)                                    |
| Повтор после неудачи        | Кулдаун; повторный заход не выдаёт бессмысленно новый «чит-набор»   |




### 3.4. Почему так

Категория через тест закрывает требование ТЗ про валидацию и даёт работодателю пул с подтверждённым уровнем, а не с самооценкой из профиля.

Шаблоны вместо LLM-вопросов дают контролируемую сложность, детерминированный подсчёт баллов и независимость от внешнего API. Шаблоны вместо одного static-банка снижают утечку ответов, но сохраняют сравнимость результатов.

Порог 70 и отказ от автодаунгрейда - честная модель «подтвердил / не подтвердил», без переписывания профиля системой.

ML тест не проводит. Backend владеет сессиями и банком вопросов, ML считает ranking и объяснения. Границы проще, дублирования меньше.

# 09. Система тестирования и подтверждения грейда

Код: `backend/app/services/testing.py`, генераторы вопросов, модели `test_*`, сиды `backend/app/seed/questions.py`. UI: `/candidate/testing`.

---

## 1. Цели

- Подтвердить пару специализация + грейд.
- Сделать кандидатов сопоставимыми внутри категории.
- Снизить утечку ответов: не один фиксированный набор вопросов на всех.
- Не понижать уже подтверждённый грейд при провале.

---

## 2. Формирование теста

| Параметр | Значение |
| -------- | -------- |
| Число вопросов | 10 (`QUESTIONS_PER_TEST`) |
| Источники | static из `test_questions` + generated по шаблонам |
| Blueprint | темы/сложность по specialization (frontend/backend и др.) |
| TTL сессии | `TEST_ATTEMPT_TTL_MIN` = 30 минут |
| Порог | `PASS_SCORE` = 70 |
| Пропуск | считается ошибкой |

Статический вопрос выходит из ротации после `STATIC_ITEM_MAX_EXPOSURES` (200) показов.

Генераторы детерминированы от seed (см. unit-тесты `test_question_generators.py`).

---

## 3. Защита от утечек

| Мера | Статус |
| ---- | ------ |
| Разные варианты у кандидатов | Да: mix static rotation + generated |
| Сопоставимая сложность | Да: blueprint по темам/грейду; не LLM-генерация «как получится» |
| Correct не на Frontend | Да: до finish (и в контракте) correct не отдаётся |
| Оценка на Backend | Да |
| Ограничение пересдач | Да: `TEST_RETRY_COOLDOWN_HOURS` = 24 для того же/более высокого grade.rank |
| Полная параметризация «уникальный тест на человека» | Частично: seed+generators, не cryptographic anti-cheat |

Ограничение MVP: банк и число специализаций с богатыми blueprint ограничены; это не промышленный proctoring.

---

## 4. Определение грейда

1. Кандидат выбирает **declared** (предполагаемый) грейд.
2. Проходит тест на выбранную пару spec+grade.
3. `score >= 70` → `verified_*` обновляются, status `verified`, audit `GRADE_CONFIRMED`.
4. Провал → declared не понижается; уже verified не откатывается; status может быть `failed` для попытки.
5. Смена подтверждённой категории: не чаще `GRADE_COOLDOWN_DAYS` = 90 (повтор той же пары разрешён).
6. После провала: пауза 24ч перед тем же/более высоким rank; более низкий — сразу.

---

## 5. Тест «под вакансию»

ТЗ (внутреннее) просит формирование заданий на основе описаний вакансий. В коде: при старте сессии учитывается `stack` / навыки для выбора шаблонов внутри темы. Отдельного полноценного «теста под конкретную вакансию работодателя» как обязательного UX-шага нет — это ограниченная механика blueprint+stack.

---

## 6. Примеры сценариев (без секретных ответов)

### Сценарий A — успешное подтверждение Middle Frontend

1. Войти как новый кандидат или использовать профиль без verified.
2. Открыть `/candidate/testing`.
3. Выбрать Frontend + Middle → старт сессии.
4. Ответить на 10 вопросов → Finish.
5. При score ≥ 70 в профиле появляется подтверждённая категория; кандидат виден в Talent Pool вакансий Frontend Middle.

### Сценарий B — разные варианты

1. Два кандидата стартуют тест той же категории.
2. Наборы `test_attempt_items` различаются (разные id/seed/порядок static).
3. Оба оцениваются по одной шкале percent correct / 10.

Демо с уже пройденным тестом: `candidate@demo.ru` (score 82, Frontend Middle) — см. seed.

## 7. Что проверить в Swagger / curl

```bash
# после login кандидата — токен в ACCESS
curl -s -X POST http://localhost:8000/api/tests/sessions \
  -H "Authorization: Bearer $ACCESS" \
  -H 'Content-Type: application/json' \
  -d '{"specializationId":"…","gradeId":"…"}'
```

История: `GET /api/tests/history`.
